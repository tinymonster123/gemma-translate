# 2026-10-19 — decode 吞吐实验（以负结果为主）

记录目标：把「哪些优化试过、为什么没用」固化下来，避免下一轮重复挖同一口井。
负结果和正结果一样是一等产物。

## 问题

20 段页面点击 → 完成约 11–12s，其中 **decode 约 8.3–9.0s（占总耗时 70%+）**，
prefill 约 2.6–2.8s。目标是把 decode 压下去。

## 方法

`npm run perf` 的跨 run 数字会被 GPU 热漂移和系统负载放大到 ±10%，小于大多数单点
优化的收益，不能用来判 A/B。

因此新增 `npm run bench`（`probes/decode-bench.mjs`）：模型只加载一次，把变体放在
**同一个 offscreen 会话**里逐轮交替（A B / B A），只比较同轮内的 ms/token。
所有数字为 4 轮中位数；机器为 Apple Silicon + Chrome 155 + WebGPU。

## 基线

| 指标 | 数值 |
|---|---:|
| decode | **29.9 ms/token**（33.5 tok/s） |
| 单次调用固定开销 | ~120–170ms（1-token 生成实测 172ms） |
| 20 段总 tokens | 305–307 |
| 长短段落 | 307 字符输入约 67 tokens；`Archives` 这种短词 2 tokens |

模型规格：Gemma 4 E2B，35 层、hidden 1536、GQA（1 个 KV head）、词表 262144、
sliding window 512、q4f16。

## 实验

| # | 假设 | 改动 | 结果 | 判定 |
|---|---|---|---|---|
| 1 | `no_repeat_ngram_size` 每 token 重建 n-gram 太贵 | 去掉，保留 repetition_penalty | 29.3 ms/token（−1.8%） | 噪声内，**无效** |
| 2 | 两个 JS logits processor 都是逐 token CPU 开销 | 全部去掉 | 29.5 ms/token（−1.4%） | 噪声内，**无效** |
| 3 | streamer 每 token detokenize + 字符串拼接有成本 | 去掉 `callback_function` | 29.9 ms/token（0.0%） | **无效** |
| 4 | system prompt 太长，诱导模型多说 | 3 种精简 prompt 对照 | 输出 65 / 66 / 67 tokens vs base 67 | **无效**：译文长度由内容决定，prompt 不影响 |
| 5 | GPU 在 dispatch 间隙空闲，两路并发能填满 | 同一会话内 2 路 `Promise.all` | 串行 30.7 tok/s → 并发 31.1 tok/s（+1.4%） | **无效**：GPU 已饱和 |
| 6 | graph capture 消除逐算子 dispatch | `session_options.enableGraphCapture` | 初始化失败：`Not supported preferred output location: cpu. Only 'gpu-buffer' location is supported when enableGraphCapture is true.` | **不可用**：采样需要 CPU 上的 logits，与 graph capture 的前置条件冲突 |
| 7 | 换小模型换吞吐 | gemma-3-270m-it | 10.4 ms/token（96 tok/s，快 2.8×） | **不可用**：译文明显崩坏（复读英文原文、串词）；本地模型有完整 chat template，不是配置问题 |

## 前序 worktree 的结论

这一轮之前有三个实验 worktree，合并或清理时把结论统一记在这里。

### `inference-timing`（`0d493f4`，已合并）

- 把一段翻译拆成 prefill（首 token 前）和 decode（首 token 后）。20 段基线：
  **prefill 3.8–4.2s、decode 8.4–8.9s、307 tokens、约 35 tok/s**。
- 确认页面 / DOM 开销只有 0–1ms，瓶颈不在渲染。
- 机器负载会显著放大计时；同一份代码在不同 load 下能差近一倍，跨 run 比较必须
  同时看 loadavg，本次所有结论都改用同会话交替 A/B。
- 当时记录「可见流式 0/20，原因未查」——本轮查明是 content script 收不到
  `runtime.sendMessage`，已修（见文末）。

### `prefix-cache`（`7536f40`，已合并）

| 指标 | 前缀关 | 前缀开 |
|---|---:|---:|
| prefill | 3.8–4.2s | **2.5–2.6s** |
| 总耗时 | 12.5–13.5s | **10.9–11.1s** |
| decode | 8.4–8.9s | 基本不变 |

- 20/20 段命中；prefill 省下约 1.4s。
- 代价：18/20 段译文逐字节一致，2/20 是等价改写（不同执行路径的浮点非确定性）。
  如果以后要求逐字节确定性，需要重新评估。

### `short-block-batching`（基于 `30d1824`，未合并，已删除）

假设：把短段落合并进一次生成，摊薄每段约 120–170ms 的固定开销。

实测（同一 run 内交替，`perf/short-block-batching-archive/` 的 5 组配对）：

| 轮次 | 不批处理 | 短段批处理 | 变化 |
|---|---:|---:|---:|
| 1 | 12.30s | 13.73s | +11.6% |
| 2 | 15.96s | 19.91s | +24.7% |
| 3 | 19.50s | 22.61s | +15.9% |
| 4 | 19.72s | 25.19s | +27.7% |
| 5 | 21.17s | 29.36s | +38.7% |

**5/5 配对都是批处理更慢，平均 17.7s → 22.2s（+25%）**，且输出长度几乎相同，
不是模型变啰嗦。判定：**负优化，证伪**。原因推断是合并后的 prompt 让模型更难
收敛到逐段短输出，生成了更多 token；具体机制未再追。

实验代码和 perf JSON 归档在 `perf/short-block-batching-archive/`
（`experiment.patch` + 三个 `perf-*.json`），worktree 已删除。

## 结论：为什么这些都不奏效

模型每 token 的成本 ≈ 35 层 × 每层约 10 个算子 × 每算子 WebGPU 开销。
29.9ms / 35 层 ≈ 0.85ms/层，和公开测量里的「每算子 ~80µs」对得上。

也就是说 **decode 是 dispatch / 同步延迟瓶颈，不是算力瓶颈**：

- 减少 JS 侧工作（实验 1–3）不碰 GPU 侧的主成本；
- 减少输出 token（实验 4）才有效，但译文长度已经由内容决定，没有水分；
- 提高并行度（实验 5）填不满，因为每 token 仍然强制一次 GPU→CPU 同步；
- dtype、量化精度同理：它们改变算力，不改变 dispatch 次数。

要让 decode 真正上一个台阶，只能减少 dispatch 次数或换运行时：

1. 换 WebLLM/MLC：公开数据里 Chrome 下 46–51 tok/s vs ORT 路线，潜在 1.4–1.5×，
   代价是引擎和模型格式重写。
2. 用 optimum / ORT transformer optimizer 重新导出 fused ONNX：论文里减少 312 次
   dispatch 换来 53% 端到端提升，但不在扩展代码范围内。
3. 更小的模型：270M 快 2.8× 但质量崩，需要找质量可接受的中间尺寸。

## 附带发现：流式从未到达页面

引擎侧 `deltaCount=61`，页面侧 0 条。原因是 offscreen 用 `runtime.sendMessage`
广播，而 **content script 收不到这类消息**，必须由 SW 用 `tabs.sendMessage` 转发。

修复后：可见流式 0/20 → 16/20（其余 4 段本身只有 1 token），长段首字从
1.0–2.1s 提前到 0.12–0.22s，总耗时不变。

冷启动首次运行仍会 0/20：253 个 delta 全部晚于响应到达，像是 SW 首次唤醒的
投递延迟；后续场景正常。未进一步追。

## 复现

```bash
npm run bench                      # 生成参数对照（默认 4 变体）
PROMPT=1 MAX_NEW=160 npm run bench # system prompt 对照
PARALLEL=2 REPEATS=3 npm run bench # 串行 vs 并发
STREAM=1 npm run bench             # 引擎侧 delta 回调 + 页面侧实际收到数
npm run perf                       # 端到端分阶段基线
```

要求：本机 Chrome、端口 8090/8099、`~/Projects/gemma-browser-lab/models/`、
从 `~/Projects/map-tile-lab` 借 Playwright。
